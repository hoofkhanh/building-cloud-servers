### 5. Linux Firewall – iptables with Docker

- **Purpose:** Enhance GCP Firewall by using Linux iptables to control network traffic directly inside the server, providing an additional layer of security for container-to-container traffic that GCP Firewall cannot filter at the container level.

- **Problem:** DOCKER-USER rules did not match traffic between containers sharing the same Docker bridge network. Both `app` and `app_test` could access `postgres:5432`, even though a DROP rule was configured.

- **Cause:** Traffic between containers on the same Linux bridge can be forwarded at Layer 2, bypassing the IPv4 iptables FORWARD chain and DOCKER-USER when bridge netfilter is not enabled.

- **Solution – Why?** Enable `br_netfilter` and set `bridge-nf-call-iptables=1` to make bridged IPv4 traffic pass through iptables hooks, allowing DOCKER-USER to inspect and filter the traffic.

**Commands:**

```bash
sudo modprobe br_netfilter
sudo sysctl -w net.bridge.bridge-nf-call-iptables=1
```

### 6. Load Balancer + MIG: Bastion, Proxies IAM Permissions

**Problem:** MIG autoscaling creates and deletes VMs with different names, making individual VM-level IAM bindings difficult to maintain.

**Solution:** Grant the Bastion service account permissions at the project level using IAM Conditions to restrict access to backend MIG instances (e.g. `app-mig-*`).

**Benefits:** Automatically covers new and recreated VMs without manually updating IAM permissions.

### 7. Network Troubleshooting – MIG Health Check Unhealthy
- **Initial approach:** Since the MIG continuously reported backend VMs as UNHEALTHY, I used the Bastion VM (which had SSH access to the backend VMs) to send requests to their private IPs and troubleshoot connectivity.

- **Purpose:** Troubleshoot connectivity layer by layer, from Bastion to the backend container, to identify why a MIG health check reports `UNHEALTHY`.

- **Problem:** Application worked locally, but Bastion could not connect to backend `10.0.1.44:8081`.

- **Troubleshooting approach:**

  1. **Test locally:** `curl localhost:8081/hello` and `curl 172.18.0.4:8080/hello` → Both returned HTTP 200. Application and container were working.

  2. **Test remotely:** `curl http://10.0.1.44:8081/hello` from Bastion → Connection timeout.

  3. **Check GCP firewall:** Inspected effective firewall rules → Expected ALLOW rules for Bastion and Google health-check source ranges on TCP 8081 were applied.

  4. **Capture backend traffic:** Used `tcpdump` on the backend network interface → Incoming SYN packets from `10.0.1.38` reached `10.0.1.44:8081`, but no SYN-ACK was observed. TCP handshake was not completed. => The request reached the backend VM, but the TCP handshake did not complete.

  5. **Inspect Linux firewall and Docker NAT:** Checked iptables → INPUT policy was ACCEPT; DOCKER-USER DROP rule only affected PostgreSQL port 5432; Docker DNAT mapping `8081 → 172.18.0.4:8080` existed. No matching application-port DROP rule was identified.

  6. **Capture Docker bridge traffic:** Used `tcpdump` on `br-d9701e26ffab` while retrying curl → No packets or SYN appeared on the Docker bridge. => No packets were observed on the Docker bridge, although SYN packets reached the VM's network interface → Suspected a problem in the host's forwarding or Docker networking path.

  7. **Check kernel networking:** Found `net.ipv4.ip_forward=0` and `net.bridge.bridge-nf-call-iptables=1` → IPv4 forwarding was disabled; bridge netfilter was already enabled.


- **Cause:** net.ipv4.ip_forward=0 disabled IPv4 forwarding, which is required for the VM to forward DNATed traffic to the Docker bridge.

- **Solution – Why?** Enable IPv4 forwarding so Linux can route DNATed traffic from VM port 8081 to container port 8080. using this command 'sudo sysctl -w net.ipv4.ip_forward=1'


  8. Verify connectivity after enabling IPv4 forwarding**
